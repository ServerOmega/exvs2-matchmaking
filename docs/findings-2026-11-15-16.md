# Findings from 15–16 November 2026

Plain-language notes from cabinet tests on **15–16 November 2026** (America/Los_Angeles), plus public
official Infinite Boost pages reviewed in mid-November. This is a custom matchmaker on private
cabinets. It is **not** affiliated with Bandai Namco.

Do not publish a VPS public IP; use `<VPS_IP>` if you need to write one down. This document has no
game-executable patch bytes, file offsets, or game hashes.

Related: the draft [exe-patching guide](exe-patching-guide.md). Setup: [SETUP.md](SETUP.md).

## Start the card servers first

Startup order matters. The game checks its card-server connection at boot and does not retry that
check. Start the **card servers first**, then the Live Monitor (LM), then the cabinets. If the LM or
the cabinets start while the card servers are down, they fail that check and never talk to the card
servers until they are restarted.

## Class Match and Mix are separate queues

On this server:

- Class Match **solo** is world **13**.
- Class Match **team** is world **14**.
- Mix / free **solo** is world **18**.
- Mix / free **team** is world **19**.

Class solo and Class team never share one Class room. That matches official Class Match G, where
solo and team have separate class tracks. A Class pair and two Class solos can all be searching at
the same time and still will not be placed together.

This server links some of those worlds (including 13 with 14, and 18 with 19) for a limited regroup
wait, so winners and losers are more likely to meet again after a match. That wait does not merge a
Class pair with Class solos into one Class room.

For a night of a pair plus two solos, use **Mix Match**, or have the two solos also pair up and
search in the team queue. Everyone should pick the same mode; a cabinet left in the wrong mode will
sit in a queue the others cannot join.

## Pairs on an unpatched cabinet

A pair that sits on a bare “finding opponents” screen is cancelled by **the game**, not the server,
after about **30 seconds**. The pair leader sends `CancelMatching` and the cabinets show a
partner-lost prompt (whether to continue with a CPU). If the two cabinets answer differently, both
can go to a black screen for about two minutes. After that, a cabinet may re-enter mid-session on
the same node id, which has led to loading-phase disconnects for the rest of the room.

The matchmaker can only answer a poll with “still waiting” or with a finished room. It cannot tell
the game to stay in search, skip that prompt, or start official-style waiting Practice. That is why
**keeping a pair in search for the full matching window needs a cabinet-side patch**, not a server
setting. See [exe-patching-guide.md](exe-patching-guide.md).

## Matchmaker settings that came out of these tests

- **`NoCpuPartner`** (default on): 2v2 modes never fill empty seats with CPU partners. Fewer than
  four human searchers wait until each cabinet’s own matching timeout (about 150 seconds), then
  return to practice and can search again. Fes 1on1 still needs only two players.
- **`ContinuePair`**: a workaround for unpatched cabinets. If a lone all-human pair has waited
  `ContinuePairSeconds` (default 18) and no four-human room has formed, the server can send them a
  room against two CPU stand-ins. That **ends** the search. Eighteen seconds is under the game’s
  ~30-second give-up; do not set this timer to 30, or it races the in-game prompt. A related
  `ContinuePairAfterCpuSeconds` setting shortens the wait when a pair has just come back from its
  own CPU room.
- **`PairNeverCpu`**: a server-only test that never sends a waiting pair a CPU room, hoping later
  humans could still be matched. On the evening of 15 November the server did keep the pair waiting,
  but at about 30 seconds the unpatched game cancelled and showed the partner-lost prompt. This
  flag is useful **after** the pair keep-searching patch is applied; it is not a substitute for that
  patch.
- **`CrossWorldTeamRooms`**: an experiment that would form one four-human room from a Class or Mix
  pair plus exactly two solos in the linked world. It was turned on and tested on real cabinets on
  16 November. Both rooms (about 1:33 PM and 1:36 PM Pacific Time) failed during loading, around 90
  to 100 seconds after the match was made. The setting was turned back **off**. Leave it off.

## Official Japanese cabinets

Summary of public official and community sources researched on 15 November 2026. Official launch of
Infinite Boost is 17 July 2025. Official operator manuals with exact timer values were not found, so
treat unpublished numbers as unconfirmed.

**Waiting for a match.** Official wording: during the matching wait for online battles, you play
Practice — officially a waiting CPU battle (対戦待ちCPU戦). You are still in the search. A human
match can still form during that fight. That is the main official / custom mismatch. Our
ContinuePair CPU send **ends** the search, so later cabinets cannot join. Official waiting Practice
does not end the search. The pair keep-searching patch is meant to get closer to that official
behaviour.

**Class Match never mixes a pair with solos.** Official Class Match G keeps solo sortie (shuffle)
and team sortie (fixed pair) on separate class tracks. Mix Match, which replaced the previous
title’s Free Match, has no solo/team split and no class filter, so a Mix room can put a fixed pair
against two solos. That mixing is a property of Mix, not of Class Match G.

**After a match.** Official cabinets are credit-driven. On a 1-credit play, winners can keep going
(up to ten wins in a row); one loss, or the ten-win cap, is GAME OVER. Our cabinets run free-play,
but the unpatched game still sends a loser to GAME OVER. Winners who continue can re-enter the queue
sooner than losers, which is one reason a continuing pair can finish a CPU fight before the losers
are even back in the queue.

## Rematch cooldown, and how to tell which cabinet dropped

Two back-to-back solo rematches on 16 November (the same four players, same teams, formed the
instant the last cabinet re-entered) ran into 21-01 errors while loading. Other solo rematches that
formed 39 seconds or more after the first re-entry played normally.

The matchmaker now holds an all-solo room that would put two nodes from the same human room back
together for `RematchCooldownSeconds` (default **30**, 0 = off) after the first of those cabinets
searches again. Other cabinets can still match in the meantime. After the cooldown, the same group
may meet again. Rooms that already include a team entry are not held this way.

To see how a room ended, use the matchmaker log (these lines are on by default):

- `ROOM-END` is printed for each cabinet after a match, with a reason
  (`reentry`, `reentry-new-node`, `cancel-after-match`, `cancel`, or `timeout`) and how many
  seconds have passed since the match was made.
- `ROOM-SUMMARY` is printed once every cabinet in that room is accounted for. It lists each
  cabinet’s reason and time, earliest first, plus the spread between the first and last end.

A cabinet that comes back around 100 seconds after the match, while the others come back much later
or never, is the one that dropped. The matchmaking protocol does not carry the cabinet-to-cabinet
disconnect result, so these lines are what the matchmaker can see.

## Online results and Class rate stuck at 1500 (+0)

Online match results are saved. After a versus match, each cabinet uploads its result to its own
card server, and those saves succeed.

Class rate, though, stayed at **1500 (+0)** for winners and losers, solo and team, in results from
14 and 16 November. The cabinet computes the rate itself; the server only stores it. The likely
cause is that the card server’s Class Match reply filled only older OverBoost-era fields, so an
Infinite Boost cabinet received an initial rate of 0 and no grade tables.

The `ClassRateTables` fix (default on in the leaderboards / card-server build) sends the IB fields:
an initial rate of 1500, grade thresholds, and class-change rates. That fix still needs a real
Class Match to confirm the rate moves after a win or a loss.

## Loading-phase 21-01 disconnects

Several four-cabinet rooms fell apart during loading on 16 November, often about 60 to 100 seconds
after the match was made, with one cabinet showing Live Monitor error **21-01** and the others
showing that communication with another player was lost. This happened in ordinary Class solo rooms
as well as in the CrossWorldTeamRooms experiment, and it was already happening before the cabinet
exe patches were applied.

What looks fine:

- The cabinets were on the same LAN. The matchmaker saw no address changes.
- Ordinary CPU load and the VPS / matchmaker side were not the cause of these drops.
- Pinning each cabinet to its own small set of CPU threads (a “CPU thread split”) did **not** help.
  Changing affinity on a running game process while a match or loading might be in progress caused
  a drop. Applying the split while the cabinets were idle later made things worse and froze games.
  Restarting the cabinets clears that split. Do not use it.

Leading suspect, not a confirmed root cause: the link between a cabinet and the Live Monitor. In
the failed rooms that were checked, the cabinet that showed 21-01 never filed a failed-battle
report, and the LM never started showing the live battle. The other cabinets then gave up with
“communication lost.” A cheap test, not yet run, is to turn off Live Battle in the LM’s test menu
while the cabinets are idle and see whether the 21-01s stop.

Separately, a five-game-copies-on-one-PC setup has had repeated Windows video-memory-management
bug checks (**0x10E**) since 14 November. Those are the host-PC crashes seen during this period.
The five copies together use most of a 16 GB graphics card, with extra video memory spilling into
system RAM. This is a host-PC issue, not a matchmaker bug. A clean reinstall or rollback of the
GPU driver, and a High performance Windows power plan, are possible next steps; they were not
applied here.

Other already-known 21-01 causes still apply: restarting the matchmaker while cabinets are queued,
or closing or crashing the LM.

## Game-side patches tested on 16 November

Scripts for these patches are **not** in this repository and are distributed privately. See the
draft [exe-patching guide](exe-patching-guide.md).

**Pair keep-searching (patch A).** After the patch was applied to all four cabinet copies, a
searching pair no longer hit the partner-lost prompt at 30 seconds. The pair stayed in search for
the full ~150-second matching window and then re-entered automatically.

**Free-play, no GAME OVER after a loss (full version).** After a full online match on 16 November
(about 3:01 PM Pacific Time), all four cabinets, losers included, searched again within half a
second of each other, with no GAME OVER and no need to re-swipe the card. Players reported that it
was working.

A hold-Start force-end patch was researched and is **on hold**. It is not recommended.
